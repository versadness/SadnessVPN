# XHTTP: совместимость параметров подписки с ядром Mihomo

Ядро: **Mihomo Meta v1.19.30, windows/amd64, go1.26.6, tags `with_gvisor`**
(`bin/mihomo.exe -v`, сборка от 16.08.2026).
Источник: <https://github.com/MetaCubeX/mihomo/releases>.

XHTTP поддерживается ядром **нативно**: `network: xhttp` + блок `xhttp-opts`.
Второго ядра в приложении нет — sing-box удалён, Xray никогда не поставлялся.
Ни один транспорт не переименовывается в XHTTP и обратно: если вариант не
поддерживается, сервер отклоняется с объяснением, а не «чинится» подменой
транспорта на HTTP/H2/gRPC.

## Как читать уровни проверки

| Уровень | Что означает |
| --- | --- |
| Парсер | Ссылка/YAML разобраны, значение дошло до внутренней модели без потерь |
| Валидатор ядра | `mihomo -t` принял сгенерированную конфигурацию (`tools/test_core_config_live.py`) |
| Соединение | Трафик реально прошёл через XHTTP-туннель (`tools/test_xhttp_loopback.py`) |

Сквозная проверка выполняется на loopback: сервером работает тот же
`bin/mihomo.exe` с VLESS-inbound и транспортом XHTTP. Цель адресуется **именем**
(`probe.invalid`), а не `127.0.0.1`, иначе клиентское правило обхода локальных
сетей увело бы запрос мимо туннеля и «успех» ничего бы не доказывал. В наборе
есть отрицательный контроль: с чужим UUID соединение обязано не состояться.

### Параметры, которые до провода не доходят

Эти ключи встречаются в ссылках Xray, но у клиента Mihomo их нет: они либо
описывают поведение **входящей** стороны, либо ограничивают только локальную
отправку и с сервером не согласуются. Они **пропускаются с записью в журнал**,
а не считаются ошибкой — иначе рабочая ссылка перестала бы импортироваться.

| Параметр | Почему пропускается |
| --- | --- |
| `scMaxConcurrentPosts` | ограничивает только собственную загрузку клиента |
| `scMaxBufferedPosts` | параметр inbound-стороны |
| `scStreamUpServerSecs` | параметр inbound-стороны |
| `noSSEHeader` | параметр inbound-стороны |
| `cMaxLifetimeMs` (XMUX) | ограничивает только время жизни соединения клиента |

Любой **другой** неизвестный ключ — это отказ с явным сообщением. Сервер не
импортируется молча «наполовину»: один несовместимый сервер не блокирует импорт
остальных, но и не притворяется рабочим.

## Сопутствующие параметры

| Параметр | Состояние | Примечание |
| --- | --- | --- |
| TLS | поддерживается | `tls: true` + `servername` |
| SNI | поддерживается | из `sni=`, иначе адрес сервера |
| ALPN | поддерживается | список; без TLS для XHTTP подставляется `http/1.1` |
| REALITY (`pbk`, `sid`) | поддерживается | `reality-opts`, проверено соединением |
| fingerprint (`fp`) | поддерживается | `client-fingerprint` |
| Пин сертификата (`pcs`) | поддерживается | `fingerprint` |
| `downloadSettings` (раздельные download/upload) | **не поддерживается** | у клиента Mihomo нет отдельного нижнего канала XHTTP; сервер отклоняется с объяснением |
| ECH | поддерживается для Hysteria 2 (`ech-opts`) | у XHTTP в ядре отдельного ECH нет |

## Что проверено на живых серверах

Живая подписка пользователя (DE/FI/LT/RU) содержит только VLESS REALITY поверх
TCP и Hysteria 2 — серверов с XHTTP в ней нет. Поэтому:

* **XHTTP подтверждён сквозным соединением на loopback**, а не на внешнем
  сервере: подходящего живого сервера с XHTTP нет, и это заявлено честно;
* Hysteria 2 подтверждён и на loopback, и на трёх живых серверах;
* VLESS REALITY подтверждён на loopback; живые REALITY-серверы подписки
  соединение не устанавливают из-за собственных параметров (`sni=example.com`),
  а не из-за клиента — см. отчёт релиза.
